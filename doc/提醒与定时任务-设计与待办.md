## 一、这是两件事

看起来像一件事，产物完全不同，所以分工也不同。

| | 提醒 | 定时任务 |
|---|---|---|
| 产物 | **告诉人一声** | **在某台机器上做一件事** |
| 最有价值的时刻 | 人**不在**电脑前 | 那台机器在线 |
| 调度在哪 | 服务端 | 服务端 |
| 执行在哪 | 所有在线端（展示） | 指定设备（PC 端跑工作流） |

两者共用一套「到点了」的调度底座，往后分叉：提醒走**投递管线**，定时任务走**派发管线**（已有的 `tasks_engine`）。

## 二、四条决定方案的事实

这四条都查证过，不是凭印象。它们直接决定了架构，别绕过去。

1. **Electron 的通知不能定时。** `Notification` 没有 `at` / `deliveryDate`，只能立刻弹 —— 「到点」必须我们自己算。
   顺带一个开发期的坑：**macOS 上未签名的构建通知根本不显示**，会发 `failed` 事件。调试看不到通知先别怀疑代码。

2. **`setTimeout` 跨系统休眠不可靠。** Node 在 macOS 上用 kevent 管定时器，机器睡过去再醒来，有报告说定时器**根本不再触发**（nodejs/node#13168，至今开着）。
   所以「一条提醒挂一个 setTimeout」这种最自然的写法，会在合盖一晚后静默失效 —— 而那恰恰是提醒最需要生效的时刻。

3. **Electron 有 `powerMonitor`**，`suspend` / `resume` 双平台都有。这是补救第 2 条的手段：醒来时强制重扫。

4. **APNs 是 best-effort 的 store-and-forward，不是可靠队列。** 设备离线时它只保留有限条（普遍报告为每设备/主题一条，靠 `apns-collapse-id` 分组），`apns-expiration` 到了还会丢。

**由此得到两条铁律，全文都建立在它们上面：**

- **不给每条提醒挂定时器。** 用「持久化的到点列表 + 短周期扫描 + 醒来补扫」。
  服务端的 `tasks_engine._watchdog_loop` 已经是这个形状（每分钟扫 `overdue_steps`），照它做。
- **推送只是敲门砖，不是数据通道。** 提醒的内容和状态**只以服务端的清单为真相**。
  客户端每次连上 / 前台化都主动拉一次「该弹但还没确认的」，靠这一步兜住所有丢推送的情况。

## 三、架构

```
                 ┌──────────────── 服务端（唯一真相源）────────────────┐
                 │  reminders 表 ── 到点扫描（复用看门狗那个循环）      │
                 │  schedules 表 ─┘        │                          │
                 └──────────────┬──────────┴──────────────────────────┘
                                │
              ┌─────────────────┼──────────────────┐
              ▼                 ▼                  ▼
        提醒：投递管线      定时任务：派发管线    离线补偿
        · WS 推 reminder     · tasks_engine       · GET /reminders/pending
          _card（在线端）      建 task 派给设备      （每次连上/前台化）
        · APNs（iOS）        · 设备离线 → 挂起
        · PC 系统通知          （已有 suspended 语义）
```

## 四、表结构

### `reminders`

```sql
CREATE TABLE IF NOT EXISTS reminders (
  id            TEXT PRIMARY KEY,
  user_id       TEXT NOT NULL,
  text          TEXT NOT NULL,          -- 提醒内容，直接显示给人看
  note          TEXT,                   -- 详情页的补充说明（可空）
  due_at        TEXT NOT NULL,          -- 下一次该响的时刻，UTC
  tz            TEXT NOT NULL,          -- 用户时区，如 Asia/Shanghai。见 §5
  repeat_rule   TEXT,                   -- NULL=不重复；见 §5 的取值
  status        TEXT NOT NULL,          -- pending | done | dismissed | overdue
  fired_at      TEXT,                   -- 上一次真正投出去的时刻
  acked_at      TEXT,                   -- 用户确认看到/处理的时刻
  snooze_until  TEXT,                   -- 「再等 10 分钟」写这里，非空时以它为准
  source        TEXT,                   -- chat | pc | ios | workflow，排查时有用
  created_at    TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_reminders_due ON reminders(status, due_at);
```

### `schedules`（定时任务）

```sql
CREATE TABLE IF NOT EXISTS schedules (
  id            TEXT PRIMARY KEY,
  user_id       TEXT NOT NULL,
  name          TEXT NOT NULL,
  device_id     TEXT,                   -- 目标设备；NULL=由服务端挑一台有该能力的
  kind          TEXT NOT NULL,          -- workflow（一期只有这一种，见 §10）
  payload       TEXT NOT NULL,          -- JSON：{workflowId, nodeId?, arg?}
  cron          TEXT,                   -- 五段 cron；和 run_once_at 二选一
  run_once_at   TEXT,                   -- 一次性，UTC
  tz            TEXT NOT NULL,
  enabled       INTEGER NOT NULL DEFAULT 1,
  next_run_at   TEXT,                   -- 算好的下一次，扫描只看这一列
  last_run_at   TEXT,
  last_task_id  TEXT,                   -- 上一次派出去的 task，便于顺着看执行详情
  created_at    TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_schedules_next ON schedules(enabled, next_run_at);
```

`next_run_at` 是**算出来存下的**，不是每次扫描时现算 cron。扫描只做一次索引范围查询，
而不是把所有 cron 都解析一遍 —— 前者随到点条数增长，后者随总条数增长。

## 五、时区与重复规则（**一期必须定死，改起来要迁数据**）

- `due_at` / `next_run_at` **一律存 UTC**，另存 `tz`。
- 「每天 9:00」在跨时区和夏令时下是**本地 9:00**，不是固定 UTC 时刻。
  所以下一次的计算必须是：取 `tz` → 在本地时区上加一天 → 再转回 UTC。
  直接给 UTC 时间戳加 86400 秒在夏令时切换那天会错一小时。
- 用户时区从哪来：设备注册时已经上报 `timezone` 和 `locale`（见 `electron/core/device/client.ts`
  的 `getRegisterInfo`），信息已经在手上，不用新做。
- `repeat_rule` 一期只支持这几种，用简单字符串而不是完整 RRULE：
  `daily` / `weekly:1,3,5`（周一三五）/ `monthly:15` / `yearly:03-15` / `cron:0 9 * * *`。
  完整 RRULE（「每月最后一个工作日」）留到有人真要再说。

## 六、触发与投递

### 扫描

挂在 `tasks_engine` 那个看门狗循环里，**不新引调度库**。服务端现在一个调度依赖都没有，
为这个引 APScheduler 不值得：每分钟扫一遍够用，而且行为可预测、好排查。

```python
async def run_watchdog_once(self):
    ...                                  # 现有的两段扫描
    await self._scan_reminders()         # 新增
    await self._scan_schedules()         # 新增
```

扫描条件：`status='pending' AND coalesce(snooze_until, due_at) <= now`。

### 投递（提醒）

到点后**先落库**（写 `fired_at`）再投递，顺序不能反 —— 反了的话投递成功但进程崩了，
重启后会再投一遍。落库在前，最坏情况是「记了但没投出去」，而那由 §7 的补偿兜住。

投递面并行三条，都当作 best-effort：

1. **在线端 WS**：`ChatHub` 推一张 `reminder_card`，形状对齐现有的 `question_card`。
2. **iOS**：APNs。payload 里**只放展示必需的最少字段** + `reminder_id`，详情让客户端拉。
3. **PC 端**：收到 WS 卡片后弹系统通知（Electron `Notification`）。

### 派发（定时任务）

到点后由 `tasks_engine` 建一个 task，目标设备执行 —— 走的就是
`doc/工作流作为设备能力-设计与待办.md` 里那条 `runHeadless` 的路。
设备离线时任务落到 `suspended`，现有的「挂太久提醒你」逻辑直接复用。

**定时任务不额外发通知。** 它的产物是「事情做了」，不是「告诉你一声」。
要知会就在工作流末尾接一个「系统通知」节点，由用户自己决定 —— 别让平台替他决定。

## 七、离线与错过的补偿（决断）

### 为什么不能只靠推送

APNs 离线时只保留有限条、还会过期（§2 第 4 条）。所以「补推」这条路天生不可靠。
**唯一可靠的办法是客户端主动对账**：每次 WS 连上、每次窗口前台化，拉一次

```
GET /reminders/pending  →  该响过、但还没 acked 的清单（含 fire_at）
```

服务端算，客户端照单显示。这一步兜住所有丢推送、断网、关机的情况。

### 错过多久之后不再逐条弹

参考了几类产品的做法：日历/提醒事项类把错过的**留在通知中心堆着并逐条列出**；
IM 类（Slack、Telegram）离线期间的消息**不逐条补推**，上线后给未读数 + 列表；
待办类（Things、Todoist）错过的变成**逾期高亮**，不再弹。

逐条补弹是这里面最差的做法 —— 开机一口气弹出昨天五条，用户下一步就是关掉通知权限。
完全不提又会真的丢事。所以取中间，**按错过时长分三级**：

| 错过时长 | 行为 |
|---|---|
| ≤ 15 分钟 | 正常弹一条，带「完成 / 再等 10 分钟」 |
| 15 分钟 ~ 当天内 | **不逐条弹**。合并成一条「你有 N 条错过的提醒」，点开进列表 |
| 超过当天 | 不弹通知。只在提醒列表里标成「已逾期」，等用户自己来看 |

**重复提醒错过时只补最近一次。** 「每天 9 点喝水」休假一周回来不该弹七条 ——
扫描时把过期的重复项直接推进到下一个未来时刻，中间跳过的不补。

## 八、幂等

幂等键是 **`reminder_id + fire_at`**（那一次触发的**计划时刻**，不是当前时间）。

用 `fire_at` 而不是当前时间，是因为同一条重复提醒会响很多次，用当前时间的话
多端各自弹出的会被算成不同的事件，去重就失效了。

三处都用这个键：

- 客户端本地记「这个键已经弹过」，重连后对账拉回同一条不重复弹。
- 「完成 / 再等」回传时带上它，服务端据此判断这次操作对应哪一次触发。
- PC 端的离线兜底（§9）与服务端推送可能都弹一次，靠它压掉。

## 九、各端要做什么

### 服务端

- 两张表 + 两段扫描（挂在看门狗循环里）。
- `reminder_card` 的 WS 推送（对齐 `question_card`）。
- 接口：增删改查、`GET /reminders/pending`、`POST /reminders/{id}/ack`（完成 / 忽略 / 再等 N 分钟）。
- APNs 通道（iOS 端上线时才需要，一期可以先只做 WS）。
- 秘书工具：`create_reminder` / `list_reminders` / `update_reminder`，让「提醒我明天 9 点开会」能落地（§11）。

### PC 端

- 提醒列表页（或并进现有某一页）+ 详情。
- 收到 `reminder_card` → 弹系统通知，带 `actions`：`完成` / `再等 10 分钟`。
  点通知**本体**（不是按钮）→ 唤起主窗口并跳到那条提醒的详情。
- **离线兜底**：服务端推下来的提醒本地留一份，断网时靠本地扫描照样弹。
  实现只许用「一分钟扫一次 + `powerMonitor.resume` 补扫」，**绝不用一条 setTimeout**（§2 第 2 条）。
- 每次 WS 连上 / 窗口前台化 → 拉一次 `pending` 对账。

### iOS 端（有客户端时）

- APNs 收到 → 系统通知，`actions` 同上。
- 点通知 → 深链进详情。深链契约现在就定下来，避免后面各端各写一套：
  `umbra://reminder/<id>`；定时任务用 `umbra://schedule/<id>`。

## 十、定时任务 = 工作流的「时间触发器」

这是本次讨论里最值得做的一处合并。

定时任务落地后，等于工作流多了一个**按时间触发**的入口。对象库里加一个
`trigger.schedule`，配置就是时间规则（和 §5 的 `repeat_rule` 同一套），
执行走服务端派发 → 设备 `runHeadless`。

三点说明：

- **要跑什么由工作流自己决定**，`schedules.kind` 一期只有 `workflow` 一种。
  这样直接复用「工作流作为设备能力」那套白名单与鉴权，不另开一条安全边界 ——
  定时执行任意脚本的风险和远程调用工作流是同一个，没道理分两处管。
- 它比 Alfred 强的地方：**电脑当时不在也能排上**，等它上线再跑（`suspended` 语义现成）。
  Alfred 的工作流没有这个能力。
- 这实际上补上了我们删掉的 `Automation Task` 想占的位。但形状不同，别照那个设计。

## 十一、自然语言建提醒：走聊天，不走快捷入口

已拍板不做进快捷入口。路径和「灵感」那条一样：用户在聊天里说
「提醒我明天下午三点开会」，秘书调 `create_reminder` 工具落库。

这么选的好处是**时间解析交给模型**，不用自己写中文时间解析（「下周三」「半小时后」
「每周一早上」）——那套东西自己写要不少代码，且边界永远修不完。

要注意的两处：

- 秘书解析出的时刻**必须回显确认**：「好，明天（7 月 31 日）15:00 提醒你开会」。
  时间这种东西解析错了用户当场看不出来，等错过了才发现，代价很大。
- 相对时间要在**服务端**换算成绝对时刻再落库，别存「明天下午三点」这种字符串。
  模型给的是相对表述，落库前必须锚定到 `tz` 上的具体 UTC 时刻。

## 十二、分期

**一期（跑通）**
`reminders` 表 + 扫描 + WS 推送；PC 端列表/详情/系统通知/`actions`；
`pending` 对账 + 分级补偿；秘书的 `create_reminder`；时区与重复规则按 §5 定死。

**二期（定时任务）**
`schedules` 表 + 扫描 + 派发到 `runHeadless`；对象库加 `trigger.schedule`；
PC 端的定时任务列表与执行历史（顺着 `last_task_id` 看现有任务详情）。

**三期（iOS 与打磨）**
APNs 通道 + 深链；提醒的批量操作；「错过的」合并卡片的交互细化。

## 十三、未决问题

- **一条提醒能不能同时是定时任务？**（「每天 9 点提醒我，并顺手跑一下同步工作流」）
  倾向**不合并** —— 两张表两个概念，合并会让「这条到底该不该弹通知」变得说不清。
  真要这种效果，就让工作流末尾接一个通知节点。
- **多设备都在线时，PC 和 iOS 会各弹一次。** 这在 IM 类产品里是常态（手机和电脑都响），
  但提醒类可能更希望「只在你正在用的那台响」。要不要做「活跃端优先」？需要活跃度信号。
- **提醒的编辑历史要不要留？** 现在 `reminders` 是可变行。改了时间之后原来的时刻就没了，
  排查「为什么昨天没响」时会缺线索。倾向加一张轻量的 `reminder_events`。
- **`snooze_until` 与 `repeat_rule` 同时存在时的语义。** 「每天 9 点」的今天这次点了
  「再等 10 分钟」，应该只影响今天这一次，不能把整条规则往后挪。实现时要专门测这一条。
- **秘书误建的提醒怎么撤。** 模型把「下周三」理解成了这周三，用户要能一句话改掉 ——
  需要 `list_reminders` + `update_reminder` 一起给，只给 create 会很难用。
