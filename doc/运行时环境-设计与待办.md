# 运行时环境（Java / Python 多版本）— 设计与待办

> 状态：**一期开工中**。写于 2026-07-30。

## 一、这个功能要解决什么

用户的原话是「之前都是通过终端去看，对于小白用户很不方便，而且有的管理的地方也不统一」。

但真正的痛点比「不方便看」深一层：**在 macOS 上，「当前用的是哪个版本」这句话没有唯一答案**。

三条查证过的事实，它们直接决定了本功能的形态：

1. **版本取决于你在哪个目录。** pyenv 官方 README 原文，选版本的顺序是：
   > "1. The `PYENV_VERSION` environment variable (if specified). 2. The application-specific `.python-version` file in the current directory (if present). 3. The first `.python-version` file found (if any) by searching each parent directory. 4. The global `$(pyenv root)/version` file."

   `.nvmrc` / `.tool-versions` / `.fvmrc` 全是同一个模式。所以「当前 Python 是 3.11」这句话，`cd` 一下就可能变成假的。

2. **版本取决于谁在问。** macOS 的 `/usr/bin/java` **不看 `JAVA_HOME`**，它自己去找最新的 JDK；而 Maven 和 Gradle 只认 `JAVA_HOME`。所以 `java -version` 和 Maven 用的可能是两个不同的 JDK —— 这正是小白用户最容易撞墙、又最查不出来的一类问题。

3. **用户说的「别名」多半不是别名。** pyenv / jenv / asdf / Volta 的版本切换靠的是 **shim**（放在 PATH 最前的包装脚本，运行时再决定调哪个真身），不是 `alias`。真正的 `alias python=…` 只活在交互式 shell 的内存里，任何子进程和 GUI 程序都看不见。

**所以本功能的产品定位是：一个「说实话的环境体检表」，而不是一个「版本切换器」。**
它的价值在于把上面这三层混乱摊开给人看 —— 装了哪些、在哪、谁在生效、为什么是它、哪里不对。

## 二、绝对不能做的事（一期红线）

**不写用户的环境。** 不改 `~/.zshrc`、不改 `$(pyenv root)/version`、不改 `JAVA_HOME`、不动任何符号链接。

理由不是保守，是**故障归因**：写坏了用户的 shell 配置，他的终端会当场不能用，而他**不会怀疑是 Umbra 干的** —— 他会以为电脑坏了，然后上网乱搜一通把环境搞得更烂。这类事故的代价远超「能在 UI 上点一下切版本」的收益。

诊断项只**告诉他该怎么改**，给出可复制的命令，由他自己在终端执行。

二期做切换时，第一个该做的也不是「切全局」，而是**写项目级版本文件**（`.python-version` / `.java-version`）——改的是项目目录里的文件，不是用户的全局环境，出错只影响一个项目且一眼可见。

## 三、探测分三层：能问就问，问不到才猜

优先级从高到低。**同一个安装被多层同时命中时，保留高层的结果**（高层知道「谁定的」，低层只知道「在哪」）。

### L1 — 问管理器（最准）

管理器自己知道版本从哪来。凡是有机器可读输出的都走这层：

| 生态 | 命令 | 能拿到什么 |
|---|---|---|
| Java | `/usr/libexec/java_home -V` | **苹果官方**枚举。版本、架构（arm64/x86_64）、厂商、完整路径 |
| Java | `/usr/libexec/java_home` | 系统认为的「默认 JDK」 |
| Python | `pyenv versions` | 全部版本 + 星号标当前 |
| Python | `pyenv version` | 官方描述："displays the currently active Python version, **along with information on how it was set**" —— 这一句是本功能最值钱的信息来源 |
| Python | `pyenv root` / `pyenv which python3` | 根目录 / 实际会调用的真身 |
| Python | `uv python list` | uv 管的版本（Python 圈正在从 pyenv 往它迁） |
| 通用 | `mise ls --json` | 唯一直接吐出 `install_path` + `source`（含 type 与 path）的工具 |
| 通用 | `asdf list` | asdf 管的版本 |

### L2 — 扫已知目录

| 生态 | 目录 |
|---|---|
| Java | `/Library/Java/JavaVirtualMachines/*/Contents/Home`（官方标准位置）· `~/.sdkman/candidates/java/*` · `/opt/homebrew/opt/openjdk*` |
| Python | `/Library/Frameworks/Python.framework/Versions/*`（python.org 安装包）· `~/.pyenv/versions/*` · `~/.local/share/uv/python/*` · `/opt/homebrew/opt/python@*` · `~/miniconda3/envs/*` |

### L3 — 兜底：扫 PATH 上**所有**同名可执行文件

现有的 `which()`（`electron/core/shared/util.ts:7-23`）是纯 fs 扫 PATH 不起子进程（很好），但**找到第一个就 return**。本功能需要「列出全部」—— 这是要新加的第一个原子能力（`whichAll`），也是揭露「PATH 上有三个 python3 在打架」的唯一手段。

### 规则表要数据驱动，不要写成 if-else

这个功能的长尾极长：uv 是近两年才起来的，mise 正在吃 asdf 的份额，明年还会有新的。探测规则做成一张**表**（`RUNTIME_SPECS`），加一个新来源就是加一行；散成 if-else 就是一份永远还不完的债。

## 四、数据模型

```ts
// 一个「装在机器上的运行时」。同一个物理安装只出现一次（按 realpath 去重）。
interface Install {
  id: string;            // 稳定 id = kind + realpath 的哈希，刷新后不变（UI 展开态不跳）
  kind: "java" | "python";
  version: string;       // 规范化后的版本号，如 "21.0.5" / "3.12.4"
  raw: string;           // 命令原始输出首行，排错用
  home: string;          // 安装根目录
  bin: string;           // 可执行文件的 realpath
  vendor: string;        // Java 的厂商（Temurin/Zulu/Oracle…），Python 留空
  arch: string;          // arm64 / x86_64 / 空
  source: string;        // 来源 key：system / homebrew / pyenv / uv / sdkman / jvm-dir / framework / conda / mise / path
  managed: boolean;      // 是否由某个版本管理器管着（决定 UI 上能不能显示「二期可切换」）
}

// 「当前生效的是哪个」——注意它是**多答案**的，不是单值。
interface Active {
  who: string;           // 谁在问：「终端里的 java」/「Maven（JAVA_HOME）」/「终端里的 python3」
  installId: string;     // 命中哪个 Install，空串=指向一个探测不到的东西
  reason: string;        // 为什么是它：「PATH 第一个匹配」/「JAVA_HOME」/「.python-version（/path/to/file）」
  path: string;          // 实际会被执行的路径
}

// 一条诊断。level 决定颜色，fix 是给用户自己去终端执行的命令（我们不代跑）。
interface Issue {
  code: string;          // J1 / P2 …，稳定标识，便于以后统计与去重
  level: "error" | "warn" | "info";
  title: string;
  detail: string;
  fix: string;           // 可复制的命令或操作说明，空串=只是提示
}

interface RuntimeScan {
  kind: "java" | "python";
  installs: Install[];
  actives: Active[];
  issues: Issue[];
  managers: { name: string; version: string; path: string }[];  // 检测到的管理器
  aliases: Record<string, string>;   // 与本语言相关的 shell 别名（见 §5）
  scannedAt: number;
  elapsedMs: number;
  partial: string[];     // 哪些探测超时/失败了 —— **必须显示**，见 §7
}
```

**`partial` 是刻意加的。** 探测是一堆会超时会失败的子进程，如果失败了就静静少一条，用户会看到一份「看起来完整其实缺东西」的清单 —— 这比报错更坏。凡是探测失败都要在 UI 上说出来。

## 五、别名 / shim / 符号链接：三种机制要分开讲

用户把这三样混为一谈了，UI 必须帮他分清，否则他会一直找不到「为什么我改了别名还是没用」。

| 机制 | 长什么样 | 谁能看见 | 怎么探测 |
|---|---|---|---|
| **shell 别名** | `alias python=/usr/bin/python3` | **只有交互式 shell**。脚本、GUI 程序、Umbra 自己都看不见 | `$SHELL -ic 'alias'`，过滤出与本语言相关的行 |
| **shim** | `~/.pyenv/shims/python3`（一个包装脚本） | 所有进程（它就在 PATH 上） | `whichAll` 命中的路径落在某个管理器的 shims 目录下 |
| **符号链接** | `/opt/homebrew/bin/python3 → ../Cellar/…` | 所有进程 | `fs.realpath` 与原路径不同 |

别名探测的代价要说清楚：`-i`（交互式）会执行用户完整的 rc 文件，可能慢、可能有副作用、可能往 stdout 打东西。所以：**超时 3 秒、失败就当没有、结果只读不改，并且在 UI 上标注「这些别名只在终端里生效」**。

现成的先例：`electron/main.ts:82-101` 的 `fixPath()` 已经在用 `$SHELL -ilc 'echo -n "__UMBRA_PATH__:$PATH"'` 抓登录 shell 的 PATH，是全仓唯一用 `-ilc` 的地方。别名走的是同一类手段。

## 六、必须做的「PATH 影子诊断」

Umbra 拿到的 PATH（`fixPath()` 之后再补了一批兜底目录）和用户终端里的 PATH **不完全一样**。如果不把这个差异摊开，第一天就会收到这样的 bug 报告：「Umbra 说是 3.12，我终端里 `python3 -V` 是 3.9」。

所以要显式对比三份 PATH：

1. Umbra 进程当前的 `process.env.PATH`
2. 登录 shell 的真实 PATH（`$SHELL -ilc`，即 `fixPath` 抓的那份）
3. 两者的差集

差异不是免责声明，**它本身就是诊断结果**：PATH 里有重复目录、shims 目录不在最前、某个管理器装了但没 init —— 这三种病都是从这里看出来的。

## 七、诊断规则清单（一期）

每条都有稳定 code，便于以后统计。`fix` 一律是给用户自己执行的命令，Umbra 不代跑。

### Java

| code | 级别 | 判定 | 说明 |
|---|---|---|---|
| `J1` | warn | `JAVA_HOME` 未设置 | Maven 会报 "The JAVA_HOME environment variable is not defined correctly"，Gradle 会找不到 Java。但 `java` 命令本身照样能跑 —— 这正是它难查的原因 |
| `J2` | error | `JAVA_HOME` 指向的目录不存在 | 卸载过 JDK 但没改配置。这个必然让所有构建工具挂掉 |
| `J3` | warn | `JAVA_HOME` 的版本 ≠ `java -version` 的版本 | macOS 的经典坑（`/usr/bin/java` 不看 `JAVA_HOME`）。**命令行和构建工具用的是两个 JDK** |
| `J4` | info | 同时装了 arm64 和 x86_64 的 JDK | Apple Silicon 上可能不知不觉跑在 Rosetta 下，性能差一截 |
| `J5` | info | 一个 JDK 都没有 | 提示怎么装 |

### Python

| code | 级别 | 判定 | 说明 |
|---|---|---|---|
| `P1` | info | PATH 上有多个**不同真身**的 `python3` | 列出全部路径并指出哪个生效。这是「为什么我 pip install 了却 import 不到」的头号原因。⚠️ 按 realpath 去重之后再计数 —— Debian 系的 `/bin` 是 `/usr/bin` 的符号链接，光数路径会把一个 python 数成两个（实测误报过） |
| `P2` | error | 装了 pyenv 但 shims 目录不在 PATH 里 | pyenv **完全没生效**。用户以为自己在用 pyenv 管版本，实际一直在用系统的 |
| `P3` | warn | 生效的是 `/usr/bin/python3`（CLT stub） | 系统那个不是给开发用的，第一次跑可能弹「安装命令行工具」的框，且不能装包 |
| `P4` | error | 当前目录（或上层）的 `.python-version` 指定了一个没装的版本 | pyenv 会直接报错，但报错信息对小白不友好 |
| `P5` | warn | `pip3 -V` 与 `python3 -m pip -V` 报的 pip 目录不同 | 装的包进了另一套 Python。用 `python3 -m pip` 是标准解法。⚠️ 判定必须比这两个 pip 的 `from` 路径，**不能**比 `sys.prefix` 与「pip 路径剥掉 site-packages」—— Debian 系用的是 `dist-packages`，后缀剥不掉会导致每台 Ubuntu 都误报（实测抓到过） |

### 通用

| code | 级别 | 判定 |
|---|---|---|
| `E1` | info | Umbra 的 PATH 与登录 shell 的 PATH 有差异（列出差集） |
| `E2` | info | PATH 里有重复目录 |
| `E3` | warn | 某项探测超时或失败（对应 `partial`），清单可能不完整 |

## 八、UI（放在「工具」里）

按用户要求：**自动扫描，不让用户手填；每个语言区域常驻一个刷新按钮。**

```
工具 → 运行时环境
┌─────────────────────────────────────────────────────┐
│ 运行时环境                                            │
│ 看清这台机器上装了哪些 Java / Python、谁在生效、哪里不对   │
├─────────────────────────────────────────────────────┤
│ ▸ Java                              [⟳ 刷新] 3 个版本  │
│   当前生效                                            │
│    终端里的 java     21.0.5 (Temurin, arm64)          │
│                     ↳ PATH 第一个匹配                  │
│    Maven/Gradle     17.0.9 (Zulu, arm64)   ⚠ 不一致   │
│                     ↳ JAVA_HOME                       │
│   ── 已安装 ───────────────────────────────           │
│    21.0.5  Temurin  arm64   /Library/Java/…  [复制路径] │
│    17.0.9  Zulu     arm64   /Library/Java/…           │
│    11.0.21 Oracle   x86_64  ~/.sdkman/…      Rosetta  │
│   ── 诊断 ─────────────────────────────────           │
│    ⚠ J3 命令行和构建工具用的不是同一个 JDK              │
│       终端里的 java 是 21.0.5，但 JAVA_HOME 指向 17.0.9 │
│       要统一的话在 ~/.zshrc 里改：                      │
│       export JAVA_HOME=$(/usr/libexec/java_home -v 21) │
│                                          [复制命令]    │
├─────────────────────────────────────────────────────┤
│ ▸ Python                            [⟳ 刷新] 5 个版本  │
│   …（同构）                                           │
│   管理器  pyenv 2.4.7 · uv 0.5.11                     │
│   别名    python → python3        仅终端内生效          │
└─────────────────────────────────────────────────────┘
```

设计要点：

- **每个语言一张独立卡片，各自有刷新按钮和各自的 loading 态。** Java 扫得快、Python 扫得慢（要跑好几个管理器命令），不能让快的等慢的。复用现成的 `RefreshButton`（`src/components/ui.tsx:153`，自带最短旋转时长，避免闪一下看不出来）。
- **「当前生效」放最上面，且允许多行。** 每行必须带 `↳ 为什么是它`。只显示一个「当前：3.12」是在撒谎（见 §1）。
- **不一致要就地标红/标黄**，不要只在诊断区说 —— 用户的眼睛先看到列表。
- **诊断的 `fix` 给一个复制按钮**，不给「一键修复」。
- **`partial` 有内容时在卡片顶部挂一条**：「有 2 项探测没完成，下面的清单可能不全」。
- 颜色沿用全局四色语义：绿=正常、橙=进行中、黄=要人处理、红=坏了。

## 九、与「能力页」的关系

**不是同一个东西，但共享探测层。**

| | 能力页 | 运行时环境 |
|---|---|---|
| 回答的问题 | AI 能用什么技能 | 我这台机器上装了什么、乱不乱 |
| 面向 | 服务端 / 秘书 | 人 |
| 数据结构 | `Manifest.version` 是**单个** `string \| null`（`registry.ts:16`） | 同一语言**多个** `Install` |

所以不合并。但有两个方向的复用：

1. 运行时探测结果可以喂给能力页的 version 字段（现在是一次性抓首行截 40 字，`config-providers.ts:46-51`）。
2. **`enginePath()`（`coding.ts:22-42`）应该建立在这一层之上。** 那段代码手写枚举 `~/.nvm/versions/node` 的所有版本目录，注释写的是为了解决「claude 找得到、node 找不到」—— 说明这个痛点早就撞上了，当时用最小成本绕过去了。有了正经探测层，agent 引擎的 PATH 问题会跟着变稳。这是本功能真实的内部收益。

## 十一、给后来改这块的人

1. **不要把探测规则从 `RUNTIME_SPECS` 里搬进 if-else。** 那张表存在的唯一理由就是「加一个新来源只改一行」。
2. **不要为了让清单看起来干净而吞掉 `partial` 和诊断。** 这个功能的全部价值就是说实话；一份漂亮但不全的清单比报错更有害。
3. **不要给诊断加「一键修复」**，除非你已经想清楚修坏了怎么回滚、以及用户怎么知道是 Umbra 改的。见 §2。
4. **别用 `which nvm` / `which pyenv` 判断管理器是否存在。** nvm 是 shell 函数（官方明确说 `which nvm` 不工作）；pyenv 虽然是真二进制，但 GUI 进程的 PATH 里可能没有它 —— 要同时看目录（`~/.pyenv`）。
5. **「谁列出来的」不等于「谁装的」。** `uv python list` **会把系统自带的 Python 也列出来**（在 Linux 容器上实测它报了 `/usr/bin/python3.11` ~ `3.13`）。来源一律用 `pythonSource()` 按**路径**判定 —— 照单全收会把系统的 Python 标成「uv 装的、由 uv 管着」，而 `managed` 这个字段二期是要决定「敢不敢显示可切换」的。
6. **每加一条诊断规则，先在真机上跑一遍看它会不会误报。** 一期这三条误报（P1 把符号链接数成两个、P5 在 Debian 上必报、uv 抢走系统 Python 的归属）全都不是逻辑写错，而是**只用样本测、没拿真环境跑**。`tests/runtimeScan.test.ts` 就是为此存在的：它拿本机真实的 python3 走一遍完整流程。诊断一旦有噪音，用户就再也不看它了。
