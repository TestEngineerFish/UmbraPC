# 工作流作为设备能力（provider / skill）— 设计与待办

> 状态：**未开工**，仅设计记录。写于 2026-07-30。
> 前置项已完成：引擎的界面依赖已收成「有人在看 / 没人在看」两套上下文，`runHeadless()` 可用。

## 一、目标

把「工作流」变成本机的一项设备能力，和 `system` / `agent` / `computer` 这些 provider 同级，
让服务端（秘书）能像调用其它技能一样调起一条工作流。

达成之后的两个直接收益：

- **用户自己搭的流程可以被 AI 调用**。用户把「导出本周报表 → 压缩 → 传到某处」搭成一条工作流，
  秘书就能在对话里直接用它，不需要我们为每个场景各写一个技能。
- **重复功能沉淀**。现在很多能力散在节点里（跑脚本、开网址、写文件）。一条搭好的工作流
  本身就是一个可复用单元，比再造一批技能便宜。

## 二、现状：已经有的地基

### 引擎侧（已完成）

```ts
// electron/core/launcher/workflow.ts
async runHeadless(wfId, nodeId, arg): Promise<{
  ok: boolean; from: string; feedback: string; error: string; outputs: RunOutput[];
}>
```

- 上下文按次运行传递（`RunCtx`），远程调用与本人操作时间交叠也不串味。
- 无人在看时：`hide`/`showPanel` 空操作；`showLargeType`/`showTextView` 的内容收进 `outputs`
  作为返回值；`action.paste` / `output.keycombo` / `utility.dialog` 被 `HEADLESS_BLOCK` 拦下
  并写明原因（往不确定的前台应用注入内容 / 要等人点按钮）。
- 拦截会先记进轨迹再中断，事后能分清「被策略拦下」和「跑到一半崩了」。

### Provider 侧（已有，不用改结构）

```ts
// electron/core/providers/registry.ts
interface Manifest { provider; display_name; kind; available; unavailable_reason; version; skills }
interface SkillSpec { description: string; params: Record<string, string> }
type Handler = (skill, params, report, confirm) => Promise<unknown>
```

- `buildRegistry(cfg)`（`providers/index.ts`）聚合所有 provider。
- 派发入口 `DeviceClient.runTask(taskId, provider, skill, params)`，附带两个能力：
  - `report(message, extra)` —— 向服务端推进度；
  - `confirm(summary, detail)` —— **向用户要一次确认**，带超时（`cfg.confirmTimeout`）。
- 停用开关已有：`cfg.disabledProviders` 命中时 `runTask` 直接拒绝。

> **`confirm` 的存在很重要**：它意味着「远程执行时也能问人一句」，只是问的不是本机弹窗，
> 而是经服务端问到用户当前在用的界面上。见第六节对 `utility.dialog` 的处置建议。

## 三、关键约束：manifest 只在注册那一刻上报

`src/services/deviceTransport.ts` 的 `sock.onopen` 里调 `getRegisterInfo()`，把 `providers`
一次性塞进 `register` 消息。**之后没有「更新能力清单」的协议**。

这一条直接决定了技能形状的选择（下一节），别绕过它去设计。

## 四、技能形状：两个方案

### 方案 A：固定两个技能（推荐先做）

```
workflow.list                      列出本机可被调用的工作流
workflow.run { id, arg }           跑指定的一条
```

- **优点**：manifest 恒定，完全不受用户增删工作流影响，和上面那条约束天然相容。
- **缺点**：秘书要先 `list` 再 `run`，多一轮；且 `list` 的结果不在 manifest 里，
  秘书对「这台机器能干什么」的先验认知里没有工作流。

### 方案 B：每条工作流一个技能

```
workflow.整理下载文件夹 { arg }
workflow.导出本周报表  { arg }
```

- **优点**：秘书在 manifest 里直接看到有哪些流程、各自描述是什么，选择质量高得多。
- **缺点**：用户改一条工作流，manifest 就变了 → 要么重连上报，要么加「更新能力清单」协议。
  技能名还得处理中文名、重名、改名（改名等于技能消失 + 新技能出现）。

### 建议

**一期做方案 A**，把契约和鉴权跑通。方案 B 的价值明确但依赖一个新协议，
等一期真跑起来、看清秘书实际怎么用之后再决定要不要加，那时也更清楚 `description` 该怎么写。

一期就把 `list` 的返回设计成「够秘书直接决策」的形状（见下节），
这样即使不进 manifest，秘书调一次 `list` 也能拿到全部信息。

## 五、契约

### `workflow.list`

参数：无（或可选 `keyword` 做过滤）。

返回：

```jsonc
{
  "workflows": [
    {
      "id": "wf_abc123",
      "name": "整理下载文件夹",
      "desc": "按类型把 ~/Downloads 分到子目录",   // 工作流的 desc 字段
      "entries": [                                  // 可用的入口节点
        { "nodeId": "n1", "kind": "trigger.keyword", "label": "关键词 dl", "argMode": "optional" }
      ],
      "needsArg": false,
      "callable": true,
      "blockedBy": []                               // 不可调用时，列出挡住它的节点
    }
  ]
}
```

`callable` / `blockedBy` 是这里最值得做的一项：**静态扫一遍节点，提前告诉秘书这条流程
远程跑不通**。链路里有 `action.paste` / `output.keycombo` / `utility.dialog` 时，
与其让秘书调用后拿到一个中途失败，不如一开始就说「这条要人在场」。

判定复用引擎里那张 `HEADLESS_BLOCK`，不要在 provider 里另抄一份。

### `workflow.run`

参数：

| 名 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 工作流 id。也允许传 `name`，但 id 优先——名字可能重复 |
| `arg` | 否 | 传给入口的参数，等价于用户在快捷入口敲的那串 |
| `nodeId` | 否 | 指定入口节点；不给就用第一个可用触发器 |
| `timeoutMs` | 否 | 整体超时，见第六节 |

返回：

```jsonc
{
  "ok": true,
  "feedback": "已写入：报告.md ✓",     // 链路最后一条反馈，给人看的一句话
  "outputs": [                          // 展示类节点收集到的内容
    { "kind": "textview", "title": "结果", "text": "…" }
  ],
  "steps": 7,                           // 跑了几个节点
  "traceId": "…"                        // 便于用户回本机的调试抽屉里对照
}
```

失败时 `ok: false` + `error`，并**保留 `outputs`** —— 失败前已经产出的东西对排查有用。

`outputs` 是现成的（`RunOutput[]`），不用新造返回体。

## 六、鉴权与安全边界

这是这件事最需要想清楚的部分，因为**工作流 provider 的风险等级和别的 provider 不是一个量级**。

### 核心风险

一条工作流可以包含 `action.script` —— 用户指定语言的任意脚本（bash / Python / Node / AppleScript）。
把工作流开放给服务端调用，实质上是**开了一个远程执行任意本机代码的入口**。

其它 provider 的技能是我们写死的、边界清楚的；工作流的内容是用户自己填的，
而「用户自己填的」在被远程调起时，和「攻击者能让秘书调起它」之间只隔着服务端的信任边界。

### 因此的几条硬要求

1. **默认关闭。** 这个 provider 的 `available` 初值为 `false`，用户在能力页显式开启。
   复用现成的 `cfg.disabledProviders` 机制即可，但**默认要在停用列表里**——
   和别的 provider 相反（别的默认可用）。这一点要在能力页文案里写清楚为什么。

2. **逐条白名单，而不是一键全开。** 新增工作流字段 `remoteCallable?: boolean`（默认 `false`）。
   用户在工作流编辑器里对某条流程显式勾选「允许被远程调用」，`list` 只列出勾了的。
   开一个总开关就把用户所有工作流一次性暴露出去，风险和收益完全不成比例。

3. **含脚本节点的工作流额外提示。** 用户勾「允许远程调用」时，如果这条流程里有 `action.script`
   或 `action.applescript`，勾选框旁边要直说：这条流程会在你的电脑上执行脚本，
   开启后秘书可以远程让它跑。不要把这句藏在折叠区里。

4. **走 `confirm` 而不是静默执行（可配）。** 工作流字段 `remoteConfirm?: boolean`。
   开启后，`workflow.run` 先调 `confirm(summary)` 要用户点头再跑。
   对「删文件」「发消息」这类流程应该默认开。

5. **token / deviceId 不用另做。** 沿用现有设备注册那套；provider 层面不引入新的凭据。

### `utility.dialog` 的处置：从「拦下」改成「问人」

现在 `HEADLESS_BLOCK` 把对话框拦下，理由是「没人可问」。但 `confirm` 机制说明**其实问得到**——
只是问到服务端那头去。

做这件事时的正确做法：给 `RunCtx` 加一个可选的 `ask?: (summary, buttons) => Promise<number>`。

- `ui` 上下文：接本机的系统消息框（现在的行为）。
- `headless` 上下文：接 provider 的 `confirm`。但 `confirm` 只有是/否两态，
  而对话框最多三个按钮 —— 要么限制远程场景只支持两按钮，要么扩展 `confirm` 的协议。
  **这一步需要服务端配合**，一期先不动，保持拦下。

## 七、引擎侧还要改的

一期真正要动引擎的地方不多，逐条列清楚：

1. **注入 —— 让 provider 拿到引擎。**
   `buildRegistry(cfg)` 现在只吃 cfg，而引擎归 `LauncherManager` 所有。
   照 `LauncherManager.setVault()` 的成例做**后置注入**，并且注入的是**窄接口**，不是整个引擎：

   ```ts
   export interface WorkflowRunner {
     listCallable(): { id: string; name: string; desc?: string; /* … */ }[];
     runHeadless(id: string, nodeId: string, arg: string): Promise<…>;
   }
   ```

   provider 只认这个接口。让 provider 直接 import `WorkflowEngine` 会把
   `node:fs` + 整个引擎拖进 provider 的依赖里，也让两边耦死。

2. **整体超时。** `runHeadless` 现在没有总超时。单个节点各有超时（脚本 20s、快捷指令 2min），
   但一条长链路可以累加到很久，而远程调用必须有上限，否则一条挂住的流程会一直占着任务。
   建议在 `runEntry` 外面包一层 `Promise.race`，超时后返回 `ok:false, error:"整体超时"`，
   并保留已产出的 `outputs`。**注意**：超时只能停止等待，停不掉已经起来的子进程，
   这一点要在文档和返回值里说明，不要假装能干净地取消。

3. **并发与共享状态。** `RunCtx` 已经按次隔离，但引擎上还有几处**跨运行的共享状态**：
   - `fileBuffers`（文件暂存区，按 `工作流id:节点id` 分桶）—— 远程调用和本人操作同时动同一个桶会互相影响。
   - `sfCache` / `sfSeq`（Script Filter 缓存与防抖）—— 只在查询路径用，远程调用走不到，暂时无碍。

   `fileBuffers` 是真问题：需要决定「远程调用是否共享用户的暂存区」。倾向**不共享**，
   给 headless 上下文一个独立的桶（键上加个前缀），否则一次远程调用可能把用户正攒着的文件取走清空。

4. **进度上报（可选，但便宜）。** `report` 已经现成。把引擎的 trace 回调接上去，
   服务端就能看到「跑到第几个节点了」。长流程很值得。

5. **`RunOutput` 里的 `feedback` 聚合。** 现在 `runEntry` 只返回最后一条 `feedback`。
   远程调用时中间节点的反馈也有价值（尤其部分失败的场景）。考虑改成也收集起来。

## 八、分期建议

**一期（跑通契约）**
`workflow` provider + `list` / `run` 两个技能；窄接口注入；默认关闭 + 逐条白名单；
`callable` / `blockedBy` 静态判定；整体超时；`fileBuffers` 独立分桶。

**二期（好用）**
`confirm` 接线（`remoteConfirm`）；进度上报；`feedback` 聚合。

**三期（要新协议）**
每条工作流一个技能（方案 B），需要「更新能力清单」协议；
`utility.dialog` 映射到远程询问，需要 `confirm` 支持多按钮。

## 九、未决问题

- 工作流的 `desc` 字段现在是可选的，且多数用户不会填。方案 A 的 `list` 里 `desc` 为空时，
  秘书凭 `name` 选择够不够？是否要在勾「允许远程调用」时**强制填一句描述**？倾向要。
- 一条工作流被远程调起时，它内部的 `action.device_skill` 会再派发一次技能。
  会不会绕出环（A 调 B，B 又调 A）？需要一个调用深度上限。
- 工作流里的 `action.ask_assistant` 在远程调用场景下 = 秘书调工作流、工作流又去问秘书。
  这条是否该在 headless 上下文里也拦下？倾向拦，理由和防环相同。
- `remoteCallable` 是工作流的字段，会跟着工作流导出。导出文件给别人时，
  这个标记应不应该被清掉？倾向导出时清掉——别人导入后不该默认可远程调用。
